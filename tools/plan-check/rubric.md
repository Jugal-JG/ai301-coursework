# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis follows the repro evidence | The plan's stated cause, read against the repro-evidence block: its numbered steps, its artifact (error text, trace, output), and especially any control run (the same steps with one thing changed). | Pass if the stated cause is consistent with every step, artifact and control in the repro evidence, and it explains why the control behaves differently from the failing run. Fail if the cause is contradicted by a control or artifact (e.g. the plan blames component X but a control run shows X working, or the artifact shows the damage already present before the step the plan blames), or if the plan never states a cause and goes straight to a change. A cause that simply restates the issue's symptom without naming a mechanism is also a fail. | required |
| One bounded change | The plan's in-scope and not-in-scope statements and its approach steps, read against the issue's title and the repro's failure. | Pass if every approach step is needed to fix the failure the repro shows, and the plan names what it will not touch. Fail if the plan bundles anything the repro does not require, even beside a correct core fix: a migration, a redesign or rewrite, a new option or settings panel, a retry or framework addition, a test-harness change, a "while I'm in the area" cleanup. A deferral stated with a reason (e.g. "the broader rework is left to a follow-up because...") is bounded and passes. | required |
| A stranger could start | The plan's approach and files/areas, read as instructions for someone who has never seen the repo. | Pass if the plan names the file(s), function(s) or component(s) to change and the chosen way of changing them, so the first edit is known without asking the author. Fail if the plan is an investigation ("profile and optimize", "poke around", "find where it goes wrong"), names no files or areas, leaves the main decision to build time ("upstream or vendored, whichever is easier", "gocui? tcell? not sure"), or lists open-ended options instead of choosing one. Stated unknowns about secondary details do not fail this check when the primary approach is chosen. | required |
| Test plan is decisive | The plan's test plan, read against the repro evidence's steps and artifact. | Pass if the test plan names an observable outcome that would differ before and after the fix (a specific output, exit code, rendered state, or a failing test that now passes), tied to the repro steps or artifact. Fail if the only test is generic ("run the full test suite", "should feel fast", "nothing else should break", "confirm it works") with no outcome specific to this fix. Extra regression checks are fine as long as the repro-based outcome is also named. | required |
| Comment follows the thread and repo asks | The plan comment, read against the thread highlights (maintainer statements, proposed fixes, requests for testing, prior PRs) and the repo-facts block's bug-report template and contribution lines. | Pass if the comment's approach follows, or explicitly explains why it diverges from, every explicit direction a maintainer or owner gave in the thread highlights (a named culprit, a proposed fix, a rejected approach, a request to test something, an open PR on the same fix), and does not contradict the repo-facts block's stated asks. Pass by default when the thread highlights hold no maintainer direction. Fail if the plan or comment picks a different route (for example documenting a workaround when the owner already isolated the code culprit and asked for testing) and never acknowledges the maintainer's direction. | required |
| AI disclosure when the repo requires it | The repo-facts block's contribution-policy line, read against the plan comment's own text. | Pass if the policy does not explicitly require disclosing AI use (silent, permissive, or only requires the human to review) or if the comment states plainly that AI assistance was used. Fail only when the policy explicitly requires disclosing AI use (tool and/or extent) and the comment says nothing about it. Every package is treated as AI-assisted work, so a stated disclosure requirement applies. | required |
| Unknowns are stated, not hidden | The plan's risks and unknowns section (or any sentence about uncertainty) and the comment's confidence, read against what the repro evidence actually shows. | Pass if the plan names at least one thing it has not verified or could go wrong when such a thing plainly exists, and nothing in the plan or comment claims certainty the repro does not support ("this will fix it for everyone", "root cause confirmed" where only a symptom was shown). Fail if the plan asserts certainty about something the evidence does not show. | preferred |
| Comment matches the plan | The plan comment compared with the candidate plan's cause, scope and test plan. | Pass if the comment states the same cause, scope and test as the plan and promises nothing the plan does not contain. Fail if the comment is boilerplate that could be pasted on any issue, or promises work the plan excludes. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. Any `required` check graded `fail` or `unclear` makes the verdict `reject`: a plan I cannot verify from the package is not ready to build from. `preferred` checks are reported but never change the verdict. A terse plan that passes every required check is accept; a long, polished, confident plan that fails one required check is reject.
